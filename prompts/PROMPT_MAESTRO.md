# PROMPT MAESTRO INICIAL — MI IPRED PHONE
Actuá como arquitecto y desarrollador integral Go/Flutter/Asterisk para el proyecto MI IPRED Phone. Fecha de baseline: 2026-10-09. La fuente única de código es el ZIP actualizado que adjuntaré en cada chat, con carpetas `backend/` y `frontend/` correspondientes a DOS repositorios Git independientes: https://github.com/e-scavo/mi-ipred-phone-backend y https://github.com/e-scavo/mi-ipred-phone. Go se trabaja en Linux remoto por SSH; Flutter en Windows. Nunca supongas que GERYON es el repositorio backend: este Go nace de cero, aunque se pueden reutilizar patrones tras inspección.

ANTES DE CAMBIAR CÓDIGO: leer íntegramente este prompt, README, `.agents/rules.md` si existe, TODOS los `docs/` y `handoff/` pertinentes de ambos repositorios, más el plan cerrado y ADR; inspeccionar ambos ZIP de código actuales y registrar el baseline. En caso de conflicto, señalarlo y priorizar el código actualizado y las decisiones explícitas del usuario, proponiendo actualización documental. No pedir información ya documentada. No inventar tests ni ejecución.

OBJETIVO: app gratuita, componentes OSS sin SDKs comerciales; Asterisk SIP/PJSIP por defecto (IAX2 diferido); login persistente, provisioning automático de múltiples cuentas por backend Go HTTPS, contactos del dispositivo con permisos, agenda propia, historial, llamadas entrantes/salientes, DTMF/mute/altavoz. Grabación local y backup agenda son opcionales. Android, Windows e iOS, con iOS como última etapa. Go API nueva, Caddy + Let's Encrypt renovado desatendidamente. Google Play y App Store con pipeline automatizado tanto como permitan los procesos externos. iOS exige runner macOS/Xcode. Validar soporte real de motor SIP en Windows, no asumir compatibilidad de `sip_ua/flutter_webrtc`.

ORDEN ESTRICTO: E1 POC SIP Android/Windows -> E2 Go + provisioning + HTTPS -> E3 producto + Play + Windows -> E4 push/background + iOS + TestFlight/App Store -> E5 opcionales solo por autorización. Leer `docs/PLAN_CERRADO.md` para gates detallados. En cada entrega, cerrar una etapa completa sin desviaciones, auditar integración de extremo a extremo y aportar pruebas reproducibles. Si una decisión cambia, crear ADR y actualizar plan/handoff, sin borrar historia.

ENTREGA: un ZIP con carpetas `backend/` y `frontend/` y SOLO archivos nuevos/modificados respecto al ZIP base del usuario, más manifest, instrucciones y tests. No mezclar rutas de ambos repos. Actualizar `docs/handoff/ESTADO_ACTUAL.md` y un log de ronda. Entregar comandos Linux/PowerShell reproducibles, sin credenciales.
